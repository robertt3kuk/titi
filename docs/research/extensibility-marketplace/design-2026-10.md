## 0. Summary

1. **The ecosystem has converged on one set of file formats.** titi can be compatible by reading them as they are.
   - Skills are `SKILL.md` with YAML frontmatter, per the [Agent Skills spec](https://agentskills.io/specification).
   - Commands are `*.md` files with `$ARGUMENTS` / `$1`.
   - Hooks use Claude Code's event → matcher → handler JSON.
   - MCP servers use the `mcpServers` map.
   - Subagents are `*.md` files with frontmatter.
   - Plugins are `.claude-plugin/plugin.json` plus `marketplace.json`.
2. **Skills are partly built in titi.** Discovery and user-typed `/name` expansion work. Gaps:
   - titi does not read `.claude/skills` or `~/.agents/skills`.
   - It has a flat-line frontmatter parser.
   - The model cannot load a skill body on its own.
3. **Custom slash commands do not exist in current code.** `STATE.md:214-226` documents a `SlashRegistry` with `$ARGUMENTS`, but `grep SlashRegistry|\$ARGUMENTS crates/` finds nothing. I suspect it was deleted with the old `App` stack (`BRAIN.md:58`) [INFERENCE].
4. **Hooks and MCP are absent.** `tools.approval` per-tool config is not wired either; approval comes only from the `--approval` flag.
5. **Gate status.**
   - L1 and L2 are passive text, like the skills that already landed. I read them as outside M6 [INFERENCE].
   - L3 hooks, L4 MCP and L6 plugins are inside M6, so they need an owner decision before starting.
   - L5 file-defined subagents sit in the M7 gate.
6. **The security model is already half built.**
   - Providers and `models` are read from user layers only (`engine.rs:533-565`), via `Settings::get_user` (`settings.rs:490`).
   - Writes into `.git/` are refused (`fs.rs:69-95`).
   - Skill and AGENTS.md text is injection-scanned.
   - Code-bearing project config (hooks, MCP servers) needs a user-side consent store keyed by content hash. Codex and Claude Code both work this way.

## 1. Survey: how other agents extend

### 1.1 Claude Code (primary format source)

**Skills** [V: [skills](https://code.claude.com/docs/en/skills)]
- Layout is `~/.claude/skills/<name>/SKILL.md` and `.claude/skills/<name>/SKILL.md`. Claude Code also walks up to the repo root and lazily loads nested directories.
- "Custom commands have been merged into skills." `.claude/commands/deploy.md` and a skill named `deploy` both create `/deploy`. If both exist, the skill wins. Subdirectories become `dir:name`.
- Frontmatter fields:
  - `name`
  - `description` (the combined `description` and `when_to_use` text is capped at 1,536 characters in the listing)
  - `argument-hint`
  - `arguments`
  - `disable-model-invocation`
  - `user-invocable`
  - `allowed-tools`
  - `disallowed-tools`
  - `model`
  - `effort`
  - `context: fork`
  - `agent`
  - `hooks`
  - `paths`
  - `shell`
  - `metadata`
  - `license`
  - `compatibility`
- Unknown fields are ignored. Bad YAML loads the skill with no fields.
- Substitutions: `$ARGUMENTS`, `$ARGUMENTS[N]`, `$N`, `$name`, `${CLAUDE_SKILL_DIR}`, `${CLAUDE_PROJECT_DIR}`, `${CLAUDE_SESSION_ID}`.
- If the body has no placeholder, the arguments are appended as `ARGUMENTS: <value>`.
- `` !`cmd` `` runs a shell command at load time and inlines its output. This is code execution from skill text.
- Skill directories are watched and reloaded live.

**Hooks** [V: [hooks reference](https://code.claude.com/docs/en/hooks)]
- Config lives in settings JSON at `~/.claude/settings.json`, `.claude/settings.json`, `.claude/settings.local.json`, managed policy, plugin `hooks/hooks.json`, and skill or agent frontmatter. Entries merge across levels.
- Shape: `{"hooks": {"PreToolUse": [{"matcher": "Bash", "hooks": [{"type": "command", "command": "...", "args": [], "if": "Bash(rm *)", "timeout": 600, "async": false, "onFailure": "block"}]}]}}`.
- Handler types are `command`, `http`, `mcp_tool`, `prompt` and `agent`.
- Events: `SessionStart`, `UserPromptSubmit`, `PreToolUse`, `PermissionRequest`, `PostToolUse`, `PostToolUseFailure`, `PostToolBatch`, `Stop`, `SubagentStart`, `SubagentStop`, `PreCompact`, `PostCompact`, `Notification`, `SessionEnd`, and more.
- Matchers: exact tool names separated by `|` or `,`, or a regex if the string has other characters. MCP tools are named `mcp__<server>__<tool>`.
- Input is JSON on stdin: `session_id`, `transcript_path`, `cwd`, `permission_mode`, `hook_event_name`, `tool_name`, `tool_input`, `tool_use_id`.
- Exit codes: 0 is success, 2 blocks (stderr is the reason), anything else is a non-blocking error.
- Exit 0 with JSON stdout allows structured control: `continue`, `stopReason`, `systemMessage`, `hookSpecificOutput.{permissionDecision (allow/deny/ask), permissionDecisionReason, updatedInput, additionalContext}`.
- Plain stdout is added as context only for `UserPromptSubmit` and `SessionStart`. Context fields are capped at 10,000 characters.
- Failure is fail-open by default. A timed-out `PreToolUse` hook does not block unless `onFailure: "block"` is set. The default timeout is 600 seconds.

**Subagents** [V: [sub-agents](https://code.claude.com/docs/en/sub-agents)]
- Files are `.claude/agents/*.md` and `~/.claude/agents/*.md`, scanned recursively, plus plugin `agents/`. Priority order is managed, then the `--agents` flag, then project, then user, then plugin.
- Frontmatter fields: `name` and `description` are required. The rest are `tools`, `disallowedTools`, `model` (an alias such as `sonnet`, a full model ID, or `inherit`), `permissionMode`, `maxTurns`, `skills`, `mcpServers`, `hooks`, `memory`, `background`, `effort`, `isolation: worktree`, `color`, `initialPrompt`.
- Plugin subagents ignore `hooks`, `mcpServers` and `permissionMode` "for security reasons".

**MCP config** [V: [mcp](https://code.claude.com/docs/en/mcp)]
- Scopes are local, project (`.mcp.json`) and user. Transports are `http` (alias `streamable-http`), `sse` (deprecated, with automatic fallback), `stdio` and `ws`.
- Claude Code sets `CLAUDE_PROJECT_DIR` in the stdio server's environment, and `${VAR}` / `${VAR:-default}` expansion works in config.
- **Project servers need approval.** A cloned repo cannot approve its own servers. `enableAllProjectMcpServers` and `enabledMcpjsonServers` committed in the project's settings are ignored until you accept the workspace trust dialog.
- Tool search defers tool definitions. On disconnect it reconnects remote servers with backoff.

**Plugins** [V: [plugins-reference](https://code.claude.com/docs/en/plugins-reference), [marketplaces](https://code.claude.com/docs/en/plugin-marketplaces)]
- `.claude-plugin/plugin.json` holds `name` (required) plus optional `version`, `userConfig`, `skills`, `commands`, `agents`, `hooks`, `mcpServers` and more.
- Default layout is `skills/`, `commands/`, `agents/`, `hooks/hooks.json`, `.mcp.json`. Components are namespaced `plugin:name`.
- `.claude-plugin/marketplace.json` holds `{name, owner, plugins[{name, source, description}]}`. A source can be a relative path, `github`, `git-subdir`, `url`, `archive`, `npm` or `command`.
- Installs are `name@marketplace`. The variables `${CLAUDE_PLUGIN_ROOT}` and `${CLAUDE_PLUGIN_DATA}` are provided.

### 1.2 OpenAI Codex CLI

- **AGENTS.md** [V: [agents-md](https://learn.chatgpt.com/docs/agent-configuration/agents-md)]
  - Global: `~/.codex/AGENTS.override.md` or `AGENTS.md`.
  - Project: walk from the git root down to the cwd, at most one file per directory. Order is `AGENTS.override.md`, then `AGENTS.md`, then names listed in `project_doc_fallback_filenames`.
  - Files are concatenated, root first, capped at 32 KiB by default (`project_doc_max_bytes`).
- **Config** [V: [config-reference](https://learn.chatgpt.com/docs/config-file/config-reference)]
  - User config is `~/.codex/config.toml`. Project `.codex/config.toml` loads only for trusted projects.
  - Project config ignores `model_provider(s)`, `openai_base_url`, `notify`, `profile(s)` and `otel`. This is the same rule titi applies to providers.
- **MCP** [V: [mcp](https://learn.chatgpt.com/docs/extend/mcp?surface=cli)]
  - Servers are `[mcp_servers.<name>]` tables with `command`, `args`, `env`, `env_vars` (an allowlist of variables to forward), `cwd`. The CLI has `codex mcp add|list|login`.
  - Transports are stdio and Streamable HTTP, with bearer and OAuth including CIMD and DCR.
  - Codex reads the server's `instructions` field.
- **Skills** [V: [build-skills](https://learn.chatgpt.com/docs/build-skills)]
  - Scanned at `$CWD/.agents/skills`, every parent up to the repo root, `~/.agents/skills`, `/etc/codex/skills`, and system.
  - Optional `agents/openai.yaml` with `policy.allow_implicit_invocation`.
  - The skills list uses about 2% of the context window, and descriptions are shortened first.
  - `[[skills.config]] path=…, enabled=false` turns one off.
- **Hooks** [V: [hooks](https://learn.chatgpt.com/docs/hooks)]
  - Same event → matcher → handler JSON as Claude Code, in `hooks.json` or inline `[hooks]` tables.
  - Only `command` and `mcp_tool` handlers run.
  - **Trust:** "Non-managed hooks must be reviewed and trusted before they run." Trust is recorded against the hook's hash, so a changed hook is skipped until re-trusted. Project-local hooks load only when the project is trusted. `--dangerously-bypass-hook-trust` exists for CI.
- Custom prompts: I did not verify the current status [UNVERIFIED]. Codex now steers authors to skills and plugins.

### 1.3 Gemini CLI

[V: [extensions](https://geminicli.com/docs/extensions/), [reference](https://geminicli.com/docs/extensions/reference/)]
- The docs banner says Gemini CLI was replaced by Antigravity CLI for unpaid and Google One users on 2026-06-18. Treat Gemini CLI as a maintenance-mode format source.
- An extension is a directory under `~/.gemini/extensions` with `gemini-extension.json`: `name`, `version`, `mcpServers` (supports `${extensionPath}`), `contextFileName` (default `GEMINI.md`), `excludeTools` (including `run_shell_command(rm -rf)`), `settings[]` with `envVar` and `sensitive` (stored in the keychain), and `plan.directory`.
- An extension can also bundle custom commands, hooks, sub-agents and skills.
- Commands are TOML files in `commands/`. `commands/gcs/sync.toml` becomes `/gcs:sync`. I did not re-verify the TOML fields [UNVERIFIED].
- Install is `gemini extensions install <github-url|path> [--ref] [--consent]`, which copies the extension. Also `update`, `enable/disable --scope user|workspace`, `link`.
- Environment sanitization: extensions and MCP servers get only safe variables plus the declared `settings[].envVar`.
- On conflicts, workspace config wins over extension config.

### 1.4 opencode

[V: [plugins](https://opencode.ai/docs/plugins/), [commands](https://opencode.ai/docs/commands/), [agents](https://opencode.ai/docs/agents/)]
- **Plugins** are JS/TS modules in `.opencode/plugins/` or `~/.config/opencode/plugins/`, or npm packages named in `opencode.json` `"plugin": [...]`.
  - A plugin exports `async ({project, client, $, directory, worktree}) => ({ "tool.execute.before": ..., "tool.execute.after": ..., event: ... })`.
  - Events include `session.idle`, `permission.asked`, `file.edited`, `tui.*`.
  - Load order is global config, project config, global plugin dir, project plugin dir.
  - Plugins run in-process. This requires a JS runtime, which a Rust binary does not have.
- **Commands** are `.opencode/commands/*.md` or JSON `command` entries. Frontmatter is `description`, `agent`, `model`, `subtask`. Placeholders are `$ARGUMENTS`, `$1..`, `` !`cmd` `` and `@file`.
- **Agents** are `.opencode/agents/*.md` with `mode: primary|subagent`, `model`, `temperature`, `steps`, `permission: {edit, shell, webfetch, ...: allow|ask|deny}` and `disable`. The `tools:` field is deprecated in favor of `permission`.

### 1.5 omp (docs only; see caveat above)

- **Skills** [V: omp://skills.md]
  - Providers are ranked by priority: native 100 (`.omp`), skillshare 95, omp-plugins 90, claude 80, agent-plugins 75, claude-plugins / agents / codex 70, opencode 55, github 30 (`.github/skills`), omp-managed 5. The first provider wins.
  - Name collisions: identical files collapse, and differing ones get `<namespace>/<name>`.
  - The system prompt carries only name and description. Bodies load through `skill://<name>/<rel>`, with `..` and symlink-escape guards. `/skill:<name>` is the user command.
  - Extra frontmatter: `globs`, `alwaysApply`, `hide`, `disable-model-invocation`, `enabled`.
  - Foreign user-level sources are opt-in; project sources load by default.
- **Slash commands** [V: omp://slash-command-internals.md]
  - Built-ins are matched first. Then extension commands, then TS or MCP commands, then file commands, then prompt templates.
  - Unknown `/x` falls through as plain prompt text.
  - Roots: `.omp/commands`, `.claude/commands/**` (a `foo/bar.md` file also registers as `foo:bar`), `.codex/commands`, `.opencode/commands`, `.agents/commands`.
  - Placeholders: `$1`, `$@[start:length]`, `$ARGUMENTS`, `$@`, quote-aware splitting, single pass.
  - If there is no placeholder, the argument text is appended.
- **Hooks** [V: omp://hooks.md]
  - `tool_call` can return `{block, reason, input, additionalContext}`. A handler error blocks the call (fail-closed).
  - `tool_result` can patch the content. A `context` event rewrites messages before each LLM call.
  - Code lives in `<cwd>/.omp/hooks/pre|post/*.ts`. Hooks are TS modules, not shell commands.
- **Task agents** [V: omp://task-agent-discovery.md]
  - `.omp/agents/*.md` and `~/.omp/agent/agents/*.md`. Frontmatter: `name`, `description`, `tools`, `spawns`, `model` (role aliases such as `@review` resolve through `modelRoles`), `thinking-level`, `output`, `blocking`, `structured`, `autoloadSkills`, `prewalk`, `advisor`.
  - **`.claude/agents`, `.codex/agents` and `.gemini/agents` are deliberately skipped** because their frontmatter schema differs. Claude-dialect plugin agents have `model` discarded.
  - Project overrides user, which overrides bundled. A bad file is skipped with a warning.
- **MCP:** `.omp/mcp.json`, `~/.omp/agent/mcp.json`, transports stdio / Streamable HTTP / legacy SSE. These details come from titi's own `docs/research/mcp/README.md`, which I did not re-verify.
- **Marketplace:** `.omp-plugin/marketplace.json` with a `.claude-plugin/` fallback (`extensibility-marketplace/README.md`).

### 1.6 Empryo (public docs only; closed binary, not run)

[V: [hooks](https://empryo.com/docs/tools/hooks.md), [skills](https://empryo.com/docs/tools/skills.md), [mcp](https://empryo.com/docs/tools/mcp.md), [agents](https://empryo.com/docs/tools/agents.md), [llms.txt](https://empryo.com/llms.txt)]
- **Hooks.** Claude-compatible format. Besides `.claude/settings.json` it also reads `.empryo/config.json`, Copilot hook files and `.codex/hooks.json`.
  - Only `type: "command"` runs. `http`, `prompt` and `mcp_tool` are skipped.
  - `failClosed: true` is available, and managed hooks fail closed by default.
  - `ask` is treated as a block, "because Empryo has no way to pause and ask you from inside a hook". titi does have an approval flow, so it can do better.
  - Every tool event gets a `tool_paths` list of every file path the call touches, including paths parsed out of shell commands.
  - Hooks get a safe environment subset with no credentials, and `EMPRYO_HOOK_ENV` can extend it.
  - Hook files in a repo "load when you open it", with no consent step. Do not copy that.
- **Skills.** Six directories: `.empryo`, `.agents`, `.claude` skills at global and project scope. Project beats global, and within a scope the order is native, then `.agents`, then `.claude`.
- **MCP.** `mcpServers` array or object, with `transport` stdio, http or sse. Tools are named `mcp__<server>__<tool>`. Stdio crashes restart up to three times. The docs say "read `mcpServers` before you open a repository you did not write", so there is no consent gate.
- **Agents.** Reads `.empryo/agents`, `.agents/agents`, `.opencode/agents`, `.gemini/agents`, `.claude/agents`. `mode: explore|code` and `tools` are enforced. A custom agent "can never get more power than the session allows".
- Plugins and SDK: only "Cells/Morphs" (desktop JSON panels) are documented. There is no plugin API relevant to titi.

### 1.7 MCP spec (current: 2026-07-28)

[V: [spec](https://modelcontextprotocol.io/specification/2026-07-28), [transports](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports), [streamable-http](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http.md), [versioning](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning.md), [authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)]

- **Protocol model.**
  - The base is JSON-RPC 2.0 and **stateless**. There is no `initialize` handshake. Every request carries protocol version, identity and client capabilities in `_meta.io.modelcontextprotocol/*`.
  - Clients may call `server/discover`. A server that does not support the requested version returns `UnsupportedProtocolVersionError` (-32022) listing what it supports.
- **Server features:** tools, resources and prompts. The client feature is elicitation. Extensions include Tasks, Skills over MCP and MCP Apps.
- **stdio.** Newline-delimited JSON-RPC to a subprocess. The client cancels with `notifications/cancelled`.
- **Streamable HTTP** (changed in 2026-07-28):
  - Every message is a separate POST to one endpoint. The client sends `Accept: application/json, text/event-stream`, and the server answers with JSON or a per-request SSE stream. Required headers are `MCP-Protocol-Version`, `Mcp-Method`, and `Mcp-Name` for `tools/call`, `resources/read` and `prompts/get`.
  - **The GET stream and protocol-level sessions are removed.** Server-to-client asks (sampling, elicitation, roots) are embedded as `InputRequiredResult` (MRTR), and the client retries with `inputResponses`.
  - Change notifications arrive through a long-lived `subscriptions/listen` POST. Closing the SSE stream cancels the request.
  - Servers must validate the `Origin` header.
- **Backward compatibility (important for a new client).**
  - A modern-only client against a legacy (≤2025-11-25) server **fails**.
  - A dual-era client probes `server/discover` on stdio, or sends a modern request on HTTP and inspects the `400` body. It falls back to `initialize` if no recognized modern error comes back, and may cache the era per server.
  - Ecosystem adoption of 2026-07-28 is not measured [UNVERIFIED]. [INFERENCE: many existing servers are still legacy, so titi must be dual-era from day one.]
  - omp's docs say omp negotiates `2025-11-25`. Claude Code runs two client runtimes, one of which adds 2026-07-28 (code.claude.com/docs/en/mcp#mcp-client-runtimes).
- **Auth** (HTTP only; stdio should read credentials from the environment):
  - OAuth 2.1 with PKCE.
  - The server MUST publish Protected Resource Metadata (RFC 9728). The client discovers the authorization server through authorization server metadata (RFC 8414) or OIDC.
  - Client registration prefers Client ID Metadata Documents, then pre-registration, then Dynamic Client Registration (now deprecated).
  - The `resource` parameter (RFC 8707) MUST be sent on both the authorization request and the token request.
  - `iss` is validated per RFC 9207. Tokens go in the `Authorization: Bearer` header only, never in the query string.
- **Security.** "Descriptions of tool behavior such as annotations should be considered untrusted, unless obtained from a trusted server". Hosts "must obtain explicit user consent before invoking any tool".
- **Cost evidence.** [Anthropic, "Code execution with MCP"](https://www.anthropic.com/engineering/code-execution-with-mcp): loading every tool definition up front is expensive, and on-demand loading cut a 150,000-token example to 2,000 tokens (98.7%).

## 3. Layered plan (smallest first)

Shared design rules:

- **R1. Compatibility by reading, not converting.** Read Claude/Codex/Agent Skills files where they are, with titi-native directories taking priority. Never write into foreign directories.
- **R2. Text is cheap to trust, code is not.**
  - Text (skills, commands, AGENTS.md) uses the existing `scan` plus path confinement.
  - Code-bearing config (hooks, MCP servers, plugins) from a project runs only if the user's trust store holds a hash of that exact definition.
  - Code-bearing config from a user layer runs unconditionally.
- **R3. Surfaces decide trust; the engine receives resolved, approved config.** The engine never reads the trust store, which keeps headless explicit.
- **R4. Hooks can tighten, never loosen.** A hook may deny or force an approval prompt. It cannot approve a tool for the user.
- **R5. No `unwrap`, typed errors, a behavioural test first.** This follows AGENTS.md. New crates need a justification under the `dependency-update` skill.

Cross-cutting path matrix (**bold** = titi-native; first match wins, project over user, native over foreign):

|---|---|---|
| Skills | **`.titi/skills`**, `.agents/skills`, `.claude/skills` (walk cwd → repo root) | **`<agent_dir>/skills`**, `~/.agents/skills`, `~/.claude/skills` |
| Commands | **`.titi/commands`**, `.agents/commands`, `.claude/commands/**` | **`<agent_dir>/commands`**, `~/.claude/commands/**` |

### L0. Workspace trust store (prerequisite for L3, L4, L6; outside the gate on its own)

**As built (2026-10-21):** done. The workspace trust store (`1501a29`, `titi-config/src/trust.rs`): a hash per definition in `<agent_dir>/trust.json`, asked once with `trust`, `once` or `no`; hooks and MCP servers of a repository both use it.

- **Value:** the one primitive every executable feature needs, and it works from day one.
- **Design.**
  - Store: `<agent_dir>/trust.json` as `{workspaces:{<canonical path>:{trusted_at, items:{<kind>:<sha256 of canonical def>:{...}}}}}`.
  - Trust is per item, in the spirit of Codex hook hashes. A changed definition loses trust until re-reviewed. Trusting a workspace does not by itself approve hooks or servers.
  - Entries are never writable by project files or by model-called tools. Add `<agent_dir>/trust.json` to the settings-tool deny list. The `settings` tool already blocks `privacy`, `providers` and `tools` (STATE 2026-10-03).
- **Surfaces.**
  - TUI: a startup panel that lists "this repo defines N hooks / M MCP servers", with accept, once, or no.
  - Headless: untrusted items are skipped and a `Notice` names them. `--trust-project` is an explicit opt-in, like Codex's bypass flag.
- **Tests (behavioural, tempdir):** a hash change revokes trust; a project settings file cannot grant trust; untrusted items are skipped with a notice; `trust.json` is unreachable from the settings tool.
- **Size:** about 300 LOC plus about 200 for the panel [INFERENCE: estimate].

### L1. Skills v2: compatibility and model-side loading (outside the gate by precedent)

**As built (2026-10-21):** done. Skills v2 with real YAML, more roots (`.titi`, `.agents`, `.claude`) and a `skill` tool (`c48e704`), the `/skills` panel (`cd41bff`).

- **Value:** existing `.claude/skills` and `~/.agents/skills` setups just work. The model can read the full instructions after seeing the list.
- **Format changes** (against [agentskills.io/specification](https://agentskills.io/specification)):
  - Real YAML frontmatter. Use `serde_yaml`, already in `titi-config`, with a per-key fallback on parse failure like omp. Do not drop the whole skill when YAML fails (Claude loads the skill with no fields).
  - Accept `name` (≤64 chars, `[a-z0-9-]`, equal to the directory name; warn instead of reject for compatibility), `description` (≤1024, kept), `license`, `compatibility`, `metadata`, `allowed-tools`.
  - Honor `disable-model-invocation` and `user-invocable: false` (hide from the model list and from `/` respectively).
  - Parse `argument-hint` and `arguments`.
  - **Do not honor `allowed-tools`, `model`, `hooks` or `` !`cmd` `` from project skills.** `allowed-tools` pre-approves tools, which breaks R4. `` !`cmd` `` is code execution on load. Honor them only from user-layer skills, and only after L3 exists [INFERENCE].
- **Roots:** add `.claude/skills` and walk cwd → repo root (Codex and Claude Code both do). Add `~/.agents/skills` and, opt-in, `~/.claude/skills`.
- **Name collisions:** keep "project beats agent", with order `.titi`, `.agents`, `.claude`. Collapse identical files by realpath as omp does. Log a Notice when two differing skills collide, so a shadowed skill is not silent.
- **Model-side loading:** two options.
  1. List each skill with its path, so the existing `read` tool loads the body. This is Codex's approach.
  2. Add a read-tier `skill` tool that takes a name and an optional relative path, confined to the skill directory and subject to the same body scan and 32 KiB cap. This is omp's `skill://` approach, but as a tool.
  - Recommend 2. It works with `read` path rules and with `describe()` so approval chips show "skill review". It also keeps skills usable in duck mode.
- **Budget:** replace the fixed cap of 32 with a character budget, like Codex's 2% of context with descriptions shortened first. Today `by_name.into_values().take(32)` drops skills alphabetically after `z`.
- **Prompt cache:** the skill list is part of the static system prompt (`runtime.rs` comment on "static for the life of the session"). Keep it that way; do not mutate it mid-session.
- **Engine/surface split:** discovery stays in `titi-engine::skills` (the CLI already calls `skills::catalog`). Only the new tool is registered at the CLI registry-build site.
- **Tests:** `.claude/skills` is found and `.titi` wins a collision; a multi-line YAML `description` parses; a symlinked `SKILL.md` out of the root is refused (the existing test pattern); the `skill` tool refuses `..` and absolute paths; a flagged body is refused with a Notice; `disable-model-invocation` hides the skill from the prompt but `/name` still works.
- **Size:** about 400 LOC plus tests [INFERENCE].

### L2. File-based slash commands (outside the gate; completes M5's "slash-команды")

**As built (2026-10-21):** done. File commands from `.titi/commands`, `.agents/commands` and `.claude/commands` (`6b5546b`), in `/` and Ctrl+K (`cd41bff`).

- **Value:** `.claude/commands/*.md` and `.opencode/commands/*.md` files work as `/name args`.
- **Format** (Claude / opencode / omp consensus):
  - A `.md` file whose name is the command. A subdirectory prefix becomes `dir:name`, and omp also registers the bare name as an alias.
  - Frontmatter keys: `description`, `argument-hint`. If `description` is absent, use the first body line, at most 60 characters, like omp.
  - Placeholders: `$ARGUMENTS`, `$1..$N`, `$ARGUMENTS[N]`. Optionally omp's `$@[start:length]`.
  - Splitting is quote-aware, and the substitution is a **single pass** so argument text containing `$1` is not re-expanded. This matters for injection.
  - If the body has no placeholder, append the arguments.
  - Skip `@file` and `` !`cmd` `` in the first cut. File inclusion could leak local files, so if added it must stay inside the workspace jail. Shell injection is excluded for the same reason as in L1.
- **Where it runs.**
  - Expansion happens in the engine, next to `expand_skills`, only when the prompt *starts* with `/name` (omp rule). That way headless gets commands too, and the transcript still shows what the user typed.
  - In `Chat::slash`, the `_ =>` arm at `chat.rs:2418` must treat a known command like it treats a known skill, and `pickers.rs:561` must list commands (`·command`).
  - Built-in names always win; a file command that shadows one is dropped with a Notice. Unknown `/x` continues to error as it does today.
- **Precedence:** built-in, then skill (Claude's rule), then command.
- **Security:** body is scanned; project command frontmatter `model` and `allowed-tools` are **ignored** (cost and approval escalation). User commands may honor `model` only if it resolves in the user's registry.
- **Protocol:** none. The engine receives ordinary text. Add `EngineCommand::ListCommands` only if the GPUI surface needs it later.
- **Tests:** `/review 123` expands `$1`; `$ARGUMENTS` is appended when there is no placeholder; an argument containing `$1` stays literal; a built-in shadow is rejected; a flagged body is refused with a Notice; headless expands the same text; a nested `ops/deploy.md` is `/ops:deploy`.
- **Size:** about 450 LOC. Reuse the discovery and body machinery from `skills.rs`, then split it only if a third caller appears.

### L3. Hooks (inside the M6 gate; needs an owner decision)

**Status (2026-10-21):** done; see "As built" below (`509d9e5`, `1484908`).

- **Value:** deterministic policy and automation. Examples: block `rm -rf`, format after edits, run checks at Stop, notify on completion, log tool calls.
- **Why command hooks and not an in-process extension API.** Codex executes only `command` and `mcp_tool`. Empryo executes only `command`. opencode and omp are in-process JS/TS, which needs an embedded JS runtime in a Rust binary [INFERENCE]. Shell commands plus JSON are language-neutral, easy to sandbox later, and an existing de-facto standard.
- **File format (Claude-compatible JSON; YAML under `hooks:` in `config.yml` is the same shape):**
```json
{"hooks": {"PreToolUse": [{"matcher": "Bash|Edit", "hooks": [
  {"type": "command", "command": "./check.sh", "args": [], "timeout": 30,
   "if": "Bash(rm *)", "onFailure": "block", "async": false}]}]}}
```
- **Events, first cut:** `PreToolUse`, `PostToolUse`, `PostToolUseFailure`, `UserPromptSubmit`, `Stop`, `SessionStart`, `SessionEnd`. Next: `PreCompact`, `SubagentStop`, `Notification`.
- **I/O contract (identical to Claude):**
  - stdin JSON: `session_id`, `cwd`, `hook_event_name`, `tool_name`, `tool_input`, `tool_use_id`, plus a `permission_mode` derived from `ApprovalMode`. Optionally Empryo's `tool_paths`.
  - Exit 0 is success, 2 blocks (stderr is the reason), anything else is a non-blocking error.
  - JSON stdout: `permissionDecision` of `deny` or `ask` (see R4), `updatedInput` (user-layer hooks only, revalidated against the tool schema), `additionalContext` (capped at 10,000 characters), `continue` / `stopReason`, `systemMessage`.
- **Tool-name mapping** [INFERENCE: the exact mapping must be checked against each tool's argument schema]: titi `bash`→`Bash`, `read`→`Read`, `write`→`Write`, `edit`/`hashline_edit`→`Edit`, `glob`→`Glob`, `grep`→`Grep`, `fetch`→`WebFetch`, `web_search`→`WebSearch`, and the `agent` tool→`Agent`. Add `file_path` as an alias of `path` in `tool_input`, so Claude-written scripts work. Native names stay matchable. MCP tools are named `mcp__server__tool` so that Claude matchers like `mcp__.*__write.*` work unchanged.
- **Engine integration** (the single choke point, `tool_loop.rs::invoke_one`):
  1. After `handler.refusal(args)` and before the tier check, run `PreToolUse`. A `deny` returns an `Executed{is_error:true, output: reason}` and never reaches approval. `ask` forces the approval prompt even under `yolo`. `allow` changes nothing.
  2. After `handler.invoke`, run `PostToolUse` or `PostToolUseFailure`. Append `additionalContext` to the tool message as a delimited, attributed note. It cannot rewrite the result in the first cut.
  3. `UserPromptSubmit` runs next to `expand_skills` (`runtime.rs:1371,1707`). A block emits a Notice and returns the text through the existing `PromptReturned`.
  4. `Stop` runs when a turn ends. An exit of 2 queues a `FollowUp` using the existing `self_commands` channel (`runtime.rs:1084`). Cap the chain so Stop hooks cannot loop forever.
  5. `SessionStart` output is added once as a context part (the way `skills` is added at `runtime.rs:2059`), so the prompt cache stays stable.
- **Runner:** a new `titi-engine/src/hooks.rs`.
  - Spawn through the process-group, timeout and SIGTERM→SIGKILL helpers already in `titi-tools/src/pipe.rs`, not a new spawn path. The engine tokio lacks `process` today.
  - Default timeout 30 s (Claude's 600 s is too long for an interactive gate). `SessionEnd` gets about 3 s.
  - Run matching hooks concurrently, deduplicate identical handlers, and send the process an environment allowlist with **no credentials**. Gemini and Empryo both scrub, and titi has `titi-secrets` keys in its own environment.
- **Failure semantics:** default fail-open like Claude and Codex, but never silent. Emit a Notice each time. Honor `onFailure: "block"`, which is fail-closed on `PreToolUse`. User-layer hooks may set it freely.
- **Trust (R2):**
  - User-layer hooks run.
  - Project-layer hooks (`.titi/hooks.json`, `.claude/settings*.json`) run only if the L0 hash is trusted. Untrusted ones are listed with a one-line warning.
  - A `disableAllHooks` key is read from user layers only.
  - **As built (2026-10-21):** the consent panel lists every pending hook with its whole command, source and short hash, and `trust`/`once` are refused until all were scrolled past. When a hook's command runs a repository file (first word a path, or the first non-flag argument after `sh`/`bash`/`python3`/`node`/…, with `$CLAUDE_PROJECT_DIR` expanded), that file's sha-256 is part of the trust hash and the panel says "runs repository files": a `git pull` that rewrites the script asks again.
  - **Residual risk, documented not closed:** what the command pulls in indirectly is not hashed. `npm run lint`, `npx eslint .`, `make check`, a linter's own config (`.eslintrc.js`, `package.json` scripts), files a hashed script itself sources or calls, and a bare name resolved through `PATH` can all change without a new hash. Closing that needs sandboxing the hook, not hashing it; until then, read a hook's command as "runs whatever this repository says that name means".
- **Planting protection:** extend the `.git` refusal in `titi-tools/src/fs.rs:69-95` to model writes into `.titi/hooks.json`, `.titi/mcp.json`, `.mcp.json`, `.claude/settings*.json` and `.claude/hooks/`. The trust hash is a second line of defence: a model-planted hook changes the hash and needs re-approval.
- **Protocol additions** (`#[non_exhaustive]`, with fixtures in `tests/protocol.rs`): `EngineEvent::HookFinished{event, hook, outcome, ms}` for the transcript and a `/hooks` list; `EngineCommand::ListHooks` → `EngineEvent::HookList`, mirroring `ListJobs`/`JobList`.
- **Deliberately not in this layer:** `http`, `prompt`, `agent` and `mcp_tool` handlers. `mcp_tool` follows L4.
- **Tests:**
  - A `PreToolUse` hook script that exits 2 blocks `bash` and the model sees the stderr reason.
  - `ask` prompts under `yolo`.
  - `allow` does not skip approval.
  - `updatedInput` is rejected from a project hook.
  - A timed-out hook is fail-open with a Notice, and fail-closed with `onFailure:"block"`.
  - An untrusted project hook is skipped, and an edited hook loses trust.
  - The hook environment contains no key variable.
  - `Stop` exit 2 queues exactly one follow-up and honors the cap.
  - The `write` tool refuses `.titi/hooks.json`.
- **Size:** about 1,000–1,300 LOC including the protocol and config parsing [INFERENCE].

### L4. MCP client (inside the M6 gate; needs an owner decision)

**Status (2026-10-21):** L4a stdio and L4b Streamable HTTP done (`2dc8e69`, `331a3cb`); L4c OAuth not started. See the two "As built" lines below.

- **Value:** the entire MCP ecosystem. Config uses the `mcpServers` shape that other agents' docs share, so server setup instructions copy across.
- **Crate:** a new `titi-mcp`.
  - Reason: JSON-RPC, transports, protocol-era detection and OAuth are a sizable self-contained concern, and `titi-core` should not take an HTTP stack. This follows the existing sketch in `docs/research/mcp/README.md`.
  - Check the official Rust MCP SDK (`rmcp`) under the `dependency-update` skill [UNVERIFIED: I did not check whether it supports 2026-07-28 or whether it is maintained]. The prior research decided on a hand-rolled client.
- **Config.**
  - `.titi/mcp.json` or `.mcp.json` (project), `<agent_dir>/mcp.json` (user), shape `{"mcpServers":{"name":{"command","args","env","cwd"}|{"type":"http","url","headers"}}}`. Accept `streamable-http` as an alias for `http`. A `url` with no `type` is a config error, as Claude Code rules.
  - `${VAR}` and `${VAR:-default}` expansion. **In a project file, expand only an allowlist of variables, and never into `url` or `headers`.** Otherwise a cloned repo can send the user's environment to an attacker host. This is the same threat as the `base_url` + `credential_env` provider issue titi already fixed (`engine.rs:520-535`).
  - Per-server options from the ecosystem: `disabled`, `timeout`, tool `include`/`exclude` globs, optional `trust` (Hermes-style).
  - `!command` secret resolution in header and env values, user layer only [from omp docs, V].
- **Transport and protocol.**
  - **Dual-era from day one** (see §1.7).
    - On stdio: send `server/discover`; fall back to `initialize` on a non-modern error.
    - On HTTP: send a modern request and inspect the 400 body.
    - Cache the era per server.
  - titi declares **no client capabilities** in the first cut (no roots, sampling or elicitation). That keeps servers from sending requests that the client cannot answer.
  - **L4a: stdio.** Newline-delimited JSON, subprocess in its own process group, environment allowlist plus the server's `env`, kill on shutdown, restart a crashed server up to three times with backoff.
  - **L4b: Streamable HTTP.** One POST per message; handle both `application/json` and `text/event-stream` replies; send `MCP-Protocol-Version`, `Mcp-Method` and `Mcp-Name`; use legacy `Mcp-Session-Id` when the server is legacy; bearer headers. Reuse the SSE reader in `titi-providers` if it is public [UNVERIFIED].
  - **L4c: OAuth 2.1.** PKCE, RFC 9728 discovery, CIMD preferred over DCR, the RFC 8707 `resource` parameter, RFC 9207 `iss` check. Needs a loopback redirect listener, opening the browser, and token storage in the `titi-secrets` auth store. Refuse tokens at a non-HTTPS token endpoint (Claude's v2 runtime does). Sub-layer is large; ship bearer headers first.
  - Skip the legacy SSE transport and WebSocket. SSE is deprecated, and Claude Code auto-falls-back from HTTP. Add a legacy SSE client only if real users need one.
- **Tool bridge.**
  - `McpToolHandler: ToolHandler`, registered in `ToolRegistry`. Name is `mcp__<server>__<tool>` (the Claude / Empryo form, so L3 matchers work). Names are limited to 64 characters (providers limit tool names [INFERENCE]); on overflow truncate and add a short hash.
  - **Approval tier is `Exec` by default**, because the registry already treats unknown tools as `Exec` and because MCP annotations are untrusted per the spec. A user-layer `tools: {include, readOnly: [...]}` entry can mark specific tools `Read` or `Network`.
  - Because titi has no "always allow this tool" memory, every MCP call prompts in `write` mode. That is a UX problem the layer will make acute. A small session-scoped allow list per tool name is worth adding alongside.
  - **Fix `ToolRegistry::register` to reject a duplicate name** (`lib.rs:188-191` overwrites silently). A server named `bash` cannot be a problem with the prefix, but two servers sanitizing to the same name could be.
  - Arguments: validate against the server's `inputSchema`. Convert MCP `content[]` blocks to text (images → a placeholder). Cap output size like the other tools. `isError:true` becomes `ToolResult.is_error`.
- **Context cost control** (Anthropic's 98.7% evidence):
  - Snapshot the tool list at session start so the registry (and the prompt cache) does not change mid-turn. Apply `list_changed` between turns or on `/mcp reload`.
  - Per-server `include` / `exclude`.
  - A budget warning when MCP specs exceed N tokens.
  - Later: a `tool_search` meta-tool that defers schemas. Claude Code does this by default.
- **Subagents:** `Exec`-tier MCP tools are withheld from read-only subagents automatically by `retain_tiers`. L5's per-agent `mcpServers` is not supported.
- **Lifecycle and surface.**
  - The CLI resolves and trust-filters servers (L0), calls `McpManager::connect(configs)` with a startup timeout, and registers the returned handlers in the registry before `start_with_tools`. Problems are reported like `registry_config_for_with_problems` (`engine.rs:548`).
  - Events: `EngineEvent::McpStatus{servers}`, `EngineCommand::ListMcp` and `McpReconnect{name}`. Mirrors `JobList`. Add fixtures to `tests/protocol.rs`.
  - `/mcp` panel (status, tool count, reconnect) in the TUI.
  - Resources and prompts are the second step. MCP prompts become `/mcp__server__prompt` commands (Claude and omp both do this). Resources become `@` mentions or a read-tier tool.
  - Elicitation and sampling only after MRTR support.
- **Trust (R2):** a user-layer server runs. A project server runs only if its hash is in `trust.json`; otherwise it shows as `pending approval`, as in Claude Code. For stdio, the approval dialog shows the full command line, since it is arbitrary code.
- **As built, L4a (2026-10-21):** stdio only, protocol **2025-11-25** (initialize / initialized, paged `tools/list`, `tools/call`, `ping` both ways, `notifications/cancelled` on timeout or a dropped call, `notifications/tools/list_changed`); older revisions a server answers with are accepted, the stateless 2026-07-28 revision (`server/discover`, no handshake) is **not** implemented, so a modern-only server fails with an unsupported-version reason. http/sse entries are skipped with a notice (L4b). No client capabilities. Config is `<agent_dir>/mcp.json`, `.titi/mcp.json`, `.mcp.json`; an entry is `{command, args, env, cwd, disabled, timeout}`; no `${VAR}` expansion, no `include`/`exclude` globs. The trust hash covers name, command, args, cwd, env keys **and values**, the capped `timeout`, and the sha-256 of **every** argument that is an existing repository file (so `deno run -A tools/mcp.ts`, `uv run server.py`, `node --import ./p.js s.js` are covered; the same lookup now hashes a hook's extra files); a launcher (`npx`, `uv`, an interpreter, …) that names no repository file is flagged in the consent panel as `repository code is not hashed` — what `npx -y pkg` or `python -m mod` pulls in stays residual risk. A project server is re-hashed before every restart and refused if it changed; `timeout` is capped at 300 s. Tool lists are bounded and screened (128 tools, 2 KB descriptions, 16 KB object-typed schemas, `titi_soul::scan` on name, description and schema), lines read from a server at 8 MiB, rendered results at 80,000 characters before masking, and the stderr log at 1 MiB; server names cannot hold `__`, and a tool name already taken is refused by `ToolRegistry::register`. A user `mcp.<server>.approval: read|write|exec` lowers the tier of the user's own servers only; a project server is always exec. Servers start in the background and the first prompt after servers are handed over waits up to 10 s for ones still starting, as a hold the engine's command loop keeps reading through (Cancel and Shutdown work meanwhile; a headless `--prompt` would otherwise run its first turn before any tool exists). A crashed server is restarted once; `/mcp restart <name>` renews that. The consent panel is the hooks panel, extended to list servers. Tool names over 64 characters are cut and end in an 8-hex hash; characters outside `[A-Za-z0-9_-]` become `_`; two tools that collide after that are reported and the second is left out. Not built: `${VAR}` expansion, `include`/`exclude`, the session allow list per tool, a token-budget warning, `tool_search`, resources and prompts, the `mcp_tool` hook handler.
- **As built, L4b (2026-10-21):** `{"type": "http"|"streamable-http", "url", "headers"}`, protocol **2025-11-25** ([Transports](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)), in `titi-mcp/src/http.rs` on the workspace `reqwest` (no new crate). One POST per message with `Accept: application/json, text/event-stream`; a JSON body or an SSE stream (multi-line `data:`, CRLF, priming events, server `ping` answered, `tools/list_changed` honoured) is read; `MCP-Session-Id` (the spec's spelling; the `Mcp-Session-Id` above is the same header, names are case-insensitive) and `MCP-Protocol-Version` are echoed after `initialize`; a 404 on a session restarts it; `DELETE` ends the session on shutdown (405 tolerated). Limits as stdio: 8 MiB per message, the server's timeout (≤300 s), the manager's tool caps and scan. **Not done:** the optional GET stream, `Last-Event-ID` resumption, `Mcp-Method`/`Mcp-Name` headers (2026 revision), OAuth (a 401 is `failed: needs auth (not supported yet)`; L4c). Redirects are not followed. Trust: user-layer entries expand `${VAR}` in url and header values at connect time; a repository entry is literal, its url must be https or http on loopback with no user information, and its hash is `{name, type, url, lowercased header names → literal values, timeout}` — never an expanded value. The consent panel shows the whole url and the header names only. A repository server is sent nothing titi holds: only its own literal headers.
- **Tests (no network):**
  - A tiny in-repo mock MCP server (a test binary speaking JSON-RPC on stdio) for initialize and discover, `tools/list`, `tools/call`, a crash, and a slow reply.
  - A loopback HTTP mock for both content types.
  - Tool-name sanitization and collision tests.
  - An untrusted project server never spawns.
  - `${SECRET}` in a project `url` is not expanded.
  - A legacy server and a modern server both work (era detection).
  - An MCP tool call goes through approval, and its tier is `Exec`.
- **Size** [INFERENCE]: L4a about 1,500–2,000 LOC, L4b about 800, L4c about 1,200.

### L5. Subagent definitions from files (inside the M7 gate)

**Status (2026-10-21):** done; see "As built" below (`166000c`, `0528d4f`, `0f3e8fa`).

- **Value:** reusable specialists, `.claude/agents` compatibility, and role-based model routing.
- **Format:** `.md` with YAML frontmatter, read from `.titi/agents`, `.agents/agents`, `.claude/agents` and the user equivalents. Fields: `name` and `description` are required; `tools`, `disallowedTools`, `model`, `maxTurns`, `skills`, `effort` optional. Unknown keys are ignored.
- **Differences from omp:** omp deliberately skips `.claude/agents` because the schemas differ. titi can read them only if it ignores the fields it cannot honor, which is the Empryo approach.
- **Mapping to titi:**
  - `tools` / `disallowedTools` need a **name-based** filter, a small `ToolRegistry::retain_names`. Today only `retain_tiers` exists (`lib.rs:~225`).
  - A definition can only **narrow** the session's tools and tier, never widen (Empryo's rule).
  - `model` honored only if it resolves in the user's registry. Claude aliases (`sonnet`, `haiku`) resolve only through the user's role map; otherwise they are ignored with a Notice (omp discards Claude-dialect `model`, Empryo maps aliases to the user's fast model).
  - The body becomes the subagent's system prompt, scanned like AGENTS.md.
  - `hooks`, `mcpServers` and `permissionMode` are ignored. Plugin subagents in Claude Code ignore the same three for security.
- **Engine:** a new `AgentDefinition` list and `EngineCommand::SpawnAgent{..}` extended with an optional `definition`. The `AgentTool` description lists each agent's name and description (Claude warns above 15,000 tokens of descriptions). Project definitions need the same body scan and carry no trust requirement since they grant nothing.
- **Tests:** a definition narrows tools; a definition cannot grant `bash` to a read-only session; an unknown alias falls back with a Notice; a flagged body is rejected; a bad file is skipped without hiding the others.
- **Size:** about 600 LOC [INFERENCE].
- **As built (2026-10-21):** `crates/titi-engine/src/agent_defs.rs`. Paths are `.titi/agents`, `.agents/agents` (flat) and `.claude/agents` (nested) from the working directory to the repository root, `<agent_dir>/agents`, and `~/.claude/agents` only under `skills.foreignUserDirs`; first claim wins and the rest are listed as shadowed. `tools` and `disallowedTools` map Claude's names (`Bash`, `Read`, `Edit`/`MultiEdit`, `Write`, `Grep`, `Glob`, `WebFetch`, `WebSearch`) to titi's and go through `ToolRegistry::retain_names` / `remove_names` on a copy of the runner's registry, so they can only narrow it; the runner's approval mode is never touched. A pattern rule (`Bash(git status)`) grants nothing in an allow-list and denies the whole tool in a deny-list, and a malformed allow-list grants nothing. `model` is `inherit`, a `modelRoles` name or an id the user's resolver accepts, else the subagents' own model plus a Notice; `maxTurns` is `min(maxTurns, agent.subagentMaxToolRounds)`; `effort` goes through `resolve_reasoning` for the model it runs on. `hooks`, `mcpServers`, `permissionMode`, `skills`, `memory`, `isolation` and `background` are read and listed as ignored. The body is capped at 32 KiB and scanned with `titi_soul::scan` with the name and description; a flagged file is invalid. The tool's `agent` parameter (and `agent` in each `tasks` entry) names a definition; the catalog is re-read when a turn starts so the description (name order, 6,000 characters) is stable within a turn. Not built: a `definition` on `EngineCommand::SpawnAgent` (only the model's tool takes one), `skills` preloading, per-definition `permissionMode`.

### L6. Plugins and marketplaces (inside the M6 gate; last)

**Status (2026-10-21):** not started.

- **Value:** one-step install of bundled skills, commands, agents, hooks and MCP servers.
- **Format:** accept `.claude-plugin/plugin.json` (optionally `.titi-plugin/` first) and `.claude-plugin/marketplace.json`, which omp also falls back to. Layout `skills/`, `commands/`, `agents/`, `hooks/hooks.json`, `.mcp.json`. Components are namespaced `plugin:name`. Support `${CLAUDE_PLUGIN_ROOT}` and `${CLAUDE_PLUGIN_DATA}`.
- **Install:**
  - `titi plugin marketplace add <path|git>`, `titi plugin install name@marketplace`.
  - Sources first: relative path and `github` / `git` with a pinned `ref` or `sha`. Skip `npm`, `archive` and `command`.
  - Copy into `<agent_dir>/plugins/<marketplace>/<name>/<version>`, and write a lock with the commit sha plus a content hash. Roll back on failure (omp does).
  - User scope only at first.
- **Trust:** installing shows a component inventory that calls out hooks and MCP servers as code. Those components follow L3 and L4 trust (hash of the installed definition). Plugin agents ignore `hooks` and `mcpServers`.
- **Scanner:** `titi_soul::scan` covers prompt-injection text only. Scripts and hooks in a plugin need a separate review prompt. A Hermes-style verdict scanner is out of scope.
- **Tests:** install from a local marketplace fixture; a failed post-install step leaves no files; a changed hook in an update needs re-trust; `plugin:name` namespacing; name collisions with built-ins rejected.
- **Size:** about 2,000–2,500 LOC [INFERENCE].
